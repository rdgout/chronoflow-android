## 1. Goal

A member on **Times** ("When is your flight?") sees one card per outbound flight, each with a Departs and an Arrives row. Each row has a **date pill** and a **time pill**. The date pill opens the Material date dialog, limited to dates on or after the previous field's moment in this airport's wall clock. The time pill opens the Material time dialog. Only **Done** writes. Between cards an information chip shows "Connection in Dubai · 2 h 40 min", "Stop in Dubai · 1 complete night" or "Stop in Dubai". A single flight shows "Flight time 11 h 35 min". Continue validates, puts errors under their card with a red ring on the date pill, and scrolls to the first error. With three or more flights the content scrolls under the fixed Continue. After Checking, a past-arrival banner can sit under the title. **Coming back?** offers One way and Add my return flight; a tap moves on after 250 ms, and taps are ignored while that is pending. **Your flight home** times reuse the Times screen.

Done means:
- Half-entered date or time values survive (in the recovery row) and are combined into the iOS wall value `YYYY-MM-DDTHH:mm` only when both halves exist. The review input never sees a half.
- The date dialog uses UTC-midnight millis of the airport wall date, so the phone's time zone never moves a date. Its lower bound is `WizardFlightTiming.minimumLocal(field)`'s date. There is no upper bound.
- The time dialog follows the **phone's** 12/24-hour setting (`DateFormat.is24HourFormat`). Pills and their accessibility values follow the **account `timeFormat`**. Both dialogs use the app language.
- Every listed board is guarded in Robolectric (light; nl on every profile, en on the narrowest) and every wrapper is captured. Two seeded emulator checks prove the language and hour-cycle rules on a real device.

## 5. The spec

### 5.1 Half-entered values (new, `:core:wizard`) [R; OQ-9d-1]

iOS stores only complete wall strings, because its one pill always writes both halves. Android has two pills, so:

- `@Serializable data class WizardPendingDateTime(val date: String? = null, val time: String? = null)`: `date` is `yyyy-MM-dd`, `time` is `HH:mm`.
- Add a field to the 9a `MemberWizardState` (`…/cw/model/MemberWizardState.kt`): `pendingDateTimes: Map<String, WizardPendingDateTime> = emptyMap()`, with `@SerialName("pendingDateTimes")`. The key is `"${leg.id}.departLocal"` or `"${leg.id}.arriveLocal"`. Keying by the leg id keeps entries stable across stop inserts. A recovery row without the key decodes to the empty map.
- Model functions (port style, next to `setDateTime`; file `…/cw/model/MemberWizardDateTimeParts.kt`):
  - `datePart(index, arrival): String?` = the complete value's first 10 characters, else the pending `date`.
  - `timePart(index, arrival): String?` = the complete value's last 5 characters, else the pending `time`.
  - `setDatePart(index, arrival, date: LocalDate)` and `setTimePart(index, arrival, hour: Int, minute: Int)`. Guard `!closed`, a valid index and `hour in 0..23`, `minute in 0..59`. Build the strings by hand with `padStart(2, '0')`, never `String.format`. If the other half exists (complete value or pending), call `setDateTime("${date}T${time}", index, arrival)` (e.g. `"2026-10-12T14:40"`) and remove the pending entry. Otherwise store the pending half and call `changed()`. Either path therefore goes through `changed()`: `entered = true`, **all** `fieldErrors` cleared (including `review`), persisted.
  - Changing one half of a complete value keeps the other half ("2026-10-12T14:40" + date 13 Oct → "2026-10-13T14:40").
- **Route edits drop every pending half:** `chooseAirport`, `swapAirports`, `removeStop`, `makeDirect` and `chooseReturn` clear `pendingDateTimes`. A route change can change the airport (and zone) a half belongs to.
- Pending halves are **not** part of `ApiTripReviewInput` and not part of the input fingerprint. `outboundComplete` and `returnComplete` stay exactly as iOS: they test only complete values, so Continue stays off while a pair is half-filled. "Please fill this in." never appears for a half.

### 5.2 Picker adapters and formats (new, `:core:wizard`, pure Kotlin) [R]

`…/cw/model/WizardPickerDates.kt`, an `object` (thin wrappers over 9a's `WizardDateTime.pickerMillis(LocalDateTime)` / `fromPickerMillis(Long)`, which already use UTC; do not add a second conversion):
- `utcMillis(date: LocalDate): Long` = `WizardDateTime.pickerMillis(date.atStartOfDay())` (`2026-10-12` → `1791763200000`; `2040-03-25` → `2216246400000`).
- `localDate(utcMillis: Long): LocalDate` = `WizardDateTime.fromPickerMillis(ms).toLocalDate()`.
- `isSelectable(utcMillis: Long, minimum: LocalDateTime?): Boolean` = `minimum == null || localDate(ms) >= minimum.toLocalDate()`. `isSelectableYear(year, minimum)` = `minimum == null || year >= minimum.year`. There is no upper bound.

UI models are `@Immutable` data classes holding raw values (`datePart`, `timePart`, `FieldMessage?`, `WizardConnection?`, `flightMinutes: Int?`), never formatted strings, so `:core:wizard` stays free of resources. Their derivation is a pure function (like 9c's `WhereUi.from`), tested on the JVM. Formatting happens in the composables through cached `remember(language, timeFormat)` lambdas. Each `WizardFlightCardUi` is a separate, equal-by-value item: a change to flight 2 must not recompose flight 1 (Task 5 test). The `TripWizardViewModel` additions handle the new `WizardEvent`s (forwarding to `setDatePart`, `setTimePart`, `chooseReturn`) and extend `continueFrom` (`finishOutbound`, `finishReturn`, `finishOutboundStep`, `finishFlightInput`), all on the main dispatcher as 9c's intents are and guarded by `closing`. The times and return UI ride in `uiState` (`WizardUiState.from`), as `where` does.
