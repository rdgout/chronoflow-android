## 1. Goal

Build Settings › Preferences › **Connectivity & reminders** (`SetReminders` and its wrappers) and the first-trip **Turn on reminders?** sheet (`WizardReminders`), porting iOS `RemindersModel`, `RemindersView`, `FirstTripRemindersSheet`, `FirstTripRemindersOffer.consume` and `RemindersDestination`.

The page has four permission states (iOS `ReminderPermission`; board `status`):

| Permission | Board status | Shows |
|---|---|---|
| `Granted` | `on` | the **Push reminders** switch; when reminders are active, the **Remind me ahead by** 15 min / 30 min / 1 hour choice |
| `Undetermined` | `ask` | "Reminders are off. When you turn them on…" and **Turn on reminders** (asks for `POST_NOTIFICATIONS` once on API 33+; below API 33 the tap itself is the opt-in) |
| `Blocked` | `blocked` | the switch (off, disabled), the warning notice, the Android steps and **Open phone settings** |
| `Unsupported` | `unsupported` | the info notice "This device can't show reminders." |

One master switch writes all four kind flags; the lead time writes `lead_min`. Both go through the `reminders` outbox to `PATCH /v1/account/reminders`. The Preferences reminders row gains its subtitle. After the first saved trip, the sheet shows **once** over that trip's page; the `wizardReminders` row moves from `pending` to `seen` **before** the sheet is shown, so a process kill, Not now or a second save never shows it again.

Done means: the ported iOS cases pass on the JVM; Robolectric guards and captures cover every state; one emulator test drives the real system permission dialog from the ask state; `make check` passes.

### 5.2 Permission mapping and request bookkeeping (`…/data/reminders/`) [R; research 07 §7.3]

12b owns the permission source and its pure mapping (12b Task 2, `ReminderPermissionMapping.kt`, already tested by 12b's `ReminderPermissionMappingTest.nativeAuthorizationMatrix`). **Do not rewrite or re-test it.** In Task 2, only check that 12b's merged `when` gives this table (it does in the 12b brief); if a row differs, fix 12b's file and add the missing row to 12b's existing test class, and say so in your report:

`fun reminderPermission(sdkInt: Int, managerAvailable: Boolean, runtimeGranted: Boolean, requestedBefore: Boolean, notificationsEnabled: Boolean, channelBlocked: Boolean): ReminderPermission` (12b's names and order; keep the merged ones)

| Condition (first match wins) | Result |
|---|---|
| `!managerAvailable` (`NotificationManager` unavailable) | `Unsupported` |
| `!requestedBefore && (sdkInt < 33 \|\| !runtimeGranted)` (below API 33 the flag is the in-app opt-in) | `Undetermined` |
| `sdkInt >= 33 && !runtimeGranted` | `Blocked` |
| `!notificationsEnabled` (`areNotificationsEnabled()`) | `Blocked` |
| `channelBlocked` (channel `reminders` exists with importance `IMPORTANCE_NONE`; a missing channel is not blocked) | `Blocked` |
| otherwise | `Granted` |

- `runtimeGranted` = `sdkInt < 33 || checkSelfPermission(POST_NOTIFICATIONS) == PERMISSION_GRANTED` (12b `ReminderPermissions.refresh()`).
- `requestedBefore` = DataStore `notificationPermissionRequested` (A5; absent → false). 12b only reads it; this phase writes it (§5.2 request start). Below API 33 it is the in-app opt-in: until **Turn on reminders** is tapped (the Reminders page or the first-trip offer), the state is `Undetermined` and nothing is scheduled (review 2026-11-16, iOS parity).
- The read runs on IO (DataStore). `Unsupported` never occurs on a real phone; it exists for the seed and the board.
- A denial after our one request reads as `Blocked`, although Android would allow a second prompt (iOS "asks once"; OQ-12c-5). A dismissed dialog (back, outside tap) also reads as `Blocked`.

**Request start** (`:app`, Task 4): `suspend fun beginPermissionRequest(): PermissionRequestStart` where `enum class PermissionRequestStart { SystemDialog, NoDialog }`:
1. If the debug override is installed (`graph.overrides.reminderPermission != null`, §5.8): call its `requestPermission()` (Undetermined → Granted, else unchanged; `permissionRequestCount++`) and return `NoDialog`.
2. Else `devicePreferences.setNotificationPermissionRequested(true)` (IO, awaited **before** the dialog, so a kill during the dialog still counts as asked). **[R]** 12b §10 says "after its request"; before is safer (a kill during the dialog) and gives the same result on API 33+, because 12b's mapping reads the flag there only while the runtime permission is not granted; below API 33 this write is the opt-in itself, and step 3 returns `NoDialog` (OQ-12c-15).
3. Return `SystemDialog` when `sdkInt >= 33 && !runtimeGranted`, else `NoDialog`. `SessionRemindersDependencies` takes `sdkInt: Int = Build.VERSION.SDK_INT`, the value `ReminderPermissions` uses, so tests can drive both.

**Permission read** (`SessionRemindersDependencies.permission()`): `graph.overrides.reminderPermission?.permission() ?: graph.reminderPermissions.refresh()`. `AppGraph` must use the same choice for `ReminderService`'s `permission` lambda (`AppGraph.kt:254`, today `{ reminderPermissions.refresh() }`) and for `SessionSettingsDependencies.reminderPermission()` (§5.7). One small `AppGraph` change: `val reminderPermission: suspend () -> ReminderPermission` built once from `overrides`, used by all three. `ReminderSessionHooks.onForeground` needs no change: it only calls `reschedule()`, which reads the permission through that lambda (R4). So the fake governs scheduling too, as iOS `MockReminderCenter` does.

**Behaviour** (Swift line numbers in brackets):
- `start()` [22–38]: if no collector job is running, launch one (`viewModelScope.launch`) that collects `deps.reminderSettings()` into `settings`, and launch `refreshPermission()` as a separate call (do **not** put it after `collect`, which never returns). While a collector runs, a second `start()` does nothing. A flow error (other than cancellation) sets `failure`.
- `stop()` [85–88]: cancel the collector job and forget it (a later `start()` collects again). `viewModelScope` cancellation covers the normal lifetime; tests call `stop()` like Swift.
- `refreshPermission()` [39–45]: `previous = permission`; `permission = deps.permission()`; if `permission == Granted && previous in {Blocked, Undetermined} && !busy` → `write(enabled = true)` (errors → `failure`). `previous == null` (first read) never writes. **[R]** the `!busy` guard is Android-only: the system dialog pauses the activity, so `ON_RESUME` fires before the launcher callback, and without the guard both paths enqueue the same patch (OQ-12c-6).
- `requestPermission()` [46–55]: `if (busy) return`; `busy = true`; `when (deps.beginPermissionRequest())`: `SystemDialog` → `permissionLaunches.send(Unit)` and return with `busy` still true; `NoDialog` → `finishPermissionRequest()`.
- `onPermissionResult()` (the launcher callback; Android-only) → `finishPermissionRequest()`.
- `finishPermissionRequest()`: `try { permission = deps.permission(); if (permission == Granted) write(true); deps.reschedule() } catch (e: CancellationException) { throw e } catch (e: Exception) { failure = e } finally { busy = false; requestsFinished.trySend(Unit) /* the channel behind permissionRequestsFinished */ }`.
- `setEnabled(enabled)` [56–61]: return unless `!busy && permission == Granted`; `busy = true`; `write(enabled)`; `busy = false` in `finally`.
- `setLead(minutes)` [62–72]: return unless `!busy && ReminderSettings.isLeadOption(minutes) && settings != null`; `busy = true`; `deps.enqueueReminders(ReminderSettings.leadPatch(minutes)!!)`; `deps.reschedule()`; errors → `failure`; `finally busy = false`. It does **not** require `Granted` (iOS).
- `write(enabled)` [73–84]: return if `settings == null`; `deps.enqueueReminders(ReminderSettings.enabledPatch(enabled))`; `failure = null`; `deps.reschedule()`.
- **Exceptions** [R, 10b rule]: `CancellationException` (including `StaleSessionException`) is rethrown and never sets `failure`; no `runCatching`. `busy` is always reset in `finally`.
- Lifetime: the collector is cancelled with `viewModelScope` (or by `stop()`).
